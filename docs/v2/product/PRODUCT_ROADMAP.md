# Visoraft V2 多平台内容自动化产品路线图

> 文档状态：规划中（`in_progress`）
> 日期：2026-08-14
> 性质：下一代产品规划，不代表任何 V2 功能已经实现

## 1. 一句话结论

V2 不应继续定位为“YouTube 转 Bilibili/AcFun 的深度搬运工具”，而应升级为：

> 面向跨平台内容团队的自动化操作系统——从多个授权来源持续发现内容，按用户配置完成清洗、适配、本地化、审批、备份和多目标发布，并能追踪每一次交付和恢复失败任务。

差异化不是只复制 Repurpose.io 的“广”，也不是只保留 V1 的“深”，而是组合成：

**多平台连接广度 × 中国/海外双向分发 × 深度媒体处理 × 可靠审批与恢复。**

## 2. V1 与 V2 的严格边界

| 维度 | V1 当前产品 | V2 下一代产品 |
| --- | --- | --- |
| 核心任务 | 完成一次深度本地化与投稿 | 长期运行用户配置的自动化工作流 |
| 来源 | 主要是 YouTube URL、搜索、频道/剧集监控 | YouTube、云盘、RSS、本地上传及后续官方平台连接 |
| 处理模型 | 固定状态机 | 受约束、可版本化、可组合工作流 |
| 目标 | Bilibili、AcFun | 多账号、多平台、云盘备份与平台发布 |
| 用户控制 | 任务和设置 | 连接、触发、过滤、处理、审批、排期、目标映射 |
| 价值单位 | 单个处理任务 | 活跃工作流与成功内容交付 |
| V1 能力在 V2 中的位置 | 主产品 | 内置复合动作 `LocalizeForChina` |

V2 不直接复用 V1 页面结构，不直接把 `youtube_monitor` 改名为 `workflow`，也不把固定任务步骤伪装成自由编排。

## 3. 目标用户和购买者

### 3.1 第一优先级：跨平台创作者与小型内容团队

- 已在 YouTube、TikTok、抖音、Bilibili 等经营多个账号。
- 每周重复下载原片、改尺寸、改文案、备份、排期和发布。
- 需要保留人工确认，但不想每个平台重复操作。
- 购买者通常是创作者本人、运营负责人或 2–10 人团队负责人。

### 3.2 第二优先级：MCN、代运营与内容工作室

- 同时管理多个客户、品牌和渠道账号。
- 需要工作区隔离、连接权限、多级审批、客户日历、失败告警和成本计量。
- 更愿意为账号规模、团队治理、SLA 和白标报告付费。

### 3.3 第三优先级：课程、播客、直播和品牌内容团队

- 长视频/音频有稳定产出，需要转码、切片建议、字幕、归档和多渠道复用。
- 内容合规和审批比“一键发布”更重要。

### 3.4 V2.0 不优先服务

- 只偶尔下载一个公开视频的免费用户。
- 无内容权利、主要诉求是绕过平台保护或批量盗搬的用户。
- 需要任意业务系统自动化的通用 Zapier/n8n 用户。
- 只需要 AI 自动找爆款片段的纯 OpusClip 用户；该能力可在后续成为处理节点，但不是首版定位。

## 4. 用户痛点与对应价值

| 用户痛点 | V2 解决方式 | 可衡量结果 |
| --- | --- | --- |
| 每个平台重复上传和填写文案 | 一份统一内容、多目标映射与自动发布 | 单条内容人工操作时间下降 |
| 内容一多就漏发、错发、重复发 | 触发游标、内容指纹、来源链、防环和目标幂等 | 重复发布率、漏发率下降 |
| 各平台尺寸、时长、码率不同 | capability manifest + 平台预设 + 发布前校验 | 目标平台拒绝率下降 |
| 不敢完全无人值守 | 条件审批、账号权限、预览、排期、暂停和 kill switch | 自动化覆盖率提高且风险可控 |
| 发布失败后不知道是否已发出 | 目标回查、未知状态对账、部分成功视图 | 不确定交付平均恢复时间下降 |
| 原片、字幕和发布版本散落 | 统一内容库、资产版本、云端备份和来源追踪 | 资产可找回率提高 |
| 跨语言发布成本高 | 复用 V1 深度字幕/翻译/QC 复合动作 | 单条本地化成本下降 |
| 团队账号容易越权 | 工作区、连接级权限、审批和审计日志 | 越权发布事件减少 |

## 5. 从竞品吸收什么

### 5.1 Repurpose.io：吸收“持续工作流”而非只抄平台列表

应吸收：

- 来源连接、内容范围、过滤、处理、目标和发布策略的一体化向导。
- 已有内容/未来内容/全部内容的启动范围。
- 尽快发布与时间表发布、每日时段和保护限额。
- 工作流复制、暂停、连接重连、手动抓取、跳过/重新加入。
- 云盘备份、尺寸适配、裁短、文案清理、首评、日历和失败诊断。

Repurpose.io 当前的平台能力按来源/目标角色和媒体类型区分，不是所有组合都可用；官方也对自动发布检测频率和批量数量设置保护。V2 必须把这些约束做成机器可读能力，而不是销售页上的平台 Logo。[平台角色与媒体类型](https://support.repurpose.io/en/article/supported-platforms-roles-and-media-types-j22278/)，[自动发布机制](https://support.repurpose.io/en/article/how-auto-publishing-works-in-repurpose-aktmnm/)

### 5.2 Zapier、Make、n8n：吸收执行语义，不复制无限画布

应吸收：条件分支、过滤、错误处理、指数退避、历史输入重放、草稿与发布版本、子工作流、运行历史。

不直接复制：任意节点、任意表达式、任意代码执行。媒体工作流的数据量、平台限制和授权风险更高，V2.0 用受约束向导能降低学习、验证和安全成本。[Zapier Paths](https://help.zapier.com/hc/en-us/articles/8496288555917-Add-branching-logic-to-Zap-workflows-with-Paths)，[n8n 执行历史](https://docs.n8n.io/workflows/executions/all-executions/)

### 5.3 Buffer、Sprout Social：吸收治理能力

应吸收：连接/渠道级发布权、需要审批权、统一草稿/待审/排期/已发/失败视图、多级审批、退回重提、过期不发布和提醒。[Buffer 审批](https://support.buffer.com/en-us/articles/managing-and-approving-draft-posts-57li7M8tDA)，[Sprout 审批工作流](https://support.sproutsocial.com/hc/en-us/articles/205974715-Message-Approval-Workflows)

## 6. V2 产品信息架构

主导航建议固定为：

1. **概览**：活跃工作流、待审批、今日排期、失败和连接异常。
2. **自动化**：模板、工作流、草稿/已发布版本、运行记录。
3. **内容库**：统一 ContentItem、原始资产、派生版本、来源和交付状态。
4. **日历**：跨平台、跨账号排期；支持筛选、拖动改期和冲突提示。
5. **审批**：待处理、已通过、退回、过期和审计。
6. **连接**：来源/目标账号、权限、过期、配额和健康状态。
7. **素材**：片头片尾、字幕样式、封面模板、品牌安全区和备份策略。
8. **分析**：交付成功率、失败原因、处理时长、用量成本和后续效果。
9. **设置**：工作区、成员、角色、通知、计费、安全和数据保留。

所有 PC 页面可见文字计算后不得低于 `12px`。

## 7. 工作流创建体验

V2.0 使用 9 步向导，右侧始终展示可执行预览：

1. 选择模板或空白工作流。
2. 选择来源连接和触发器。
3. 选择内容范围：未来、历史起点、手动选中。
4. 配置过滤：媒体类型、时长、关键词、语言、发布时间、标签。
5. 添加处理：清洁源、尺寸、裁切、字幕、元数据、本地化、备份。
6. 设置控制：自动、每条审批、条件审批、预算和配额。
7. 添加一个或多个目标账号，并配置目标字段映射。
8. 设置立即/队列/排期、时区、时间窗、最小间隔和每日上限。
9. 用一条样例做 dry run，通过静态检查后发布不可变版本。

编辑中的草稿不会影响正在运行的生产版本。重新发布产生新版本；旧运行仍保留原配置快照。

## 8. 功能分期

### 8.1 V2.0：Automation Foundation

必须包含：

- 工作区、成员基础角色和连接凭证库。
- 连接器目录、能力清单和连接健康。
- 来源触发、过滤、线性处理、条件审批、多目标发布与备份。
- 草稿、校验、dry run、不可变发布版本、暂停/恢复和运行记录。
- 统一 ContentItem、MediaAsset、来源链、指纹和 Delivery。
- 尺寸适配、crop/pad、起止裁切、音量/帧率/码率标准化、字幕保留/烧录、片头片尾、元数据模板。
- V1 `LocalizeForChina` 复合动作。
- 立即、队列下一时段、指定时间、时间窗、每日上限、最小间隔。
- 每目标部分成功、失败重试、不确定状态回查和人工处置。
- 全渠道内容列表、待审批列表、发布日历和告警。

### 8.2 V2.1：Growth & Governance

- 条件分支、受控并行分支和可复用子流程。
- 多级审批、客户/品牌空间、连接级细分权限。
- AI 文案、标题/标签改写、首评、平台字段模板。
- 固定角标裁切/静态区域修复，强制预览确认。
- 静音检测、时间点建议、固定规则拆片。
- 发布后指标回填、活动标签和成本分析。
- 更多已审核官方连接器。

### 8.3 V2.2：Intelligent Repurposing

- 智能主体重构图、自动安全区和镜头跟踪。
- 长视频高光建议与多片段批量生成。
- 动态水印实验处理，限定用户自有/授权内容。
- 生成式扩画、品牌模板和多语言文案测试。
- 连接器开发者 SDK 和经过审核的私有连接器。

## 9. 发布控制必须做到什么

- 发布模式：立即、下一空档、指定时间、允许时间窗、仅存草稿。
- 时间规则：工作区默认时区、账号时区、夏令时、黑名单日期。
- 保护规则：账号每小时/每日上限、最小间隔、活动总上限、全局 kill switch。
- 目标字段：标题、正文、标签、隐私、分类、合集/播放列表、受众、首评、封面。
- 治理规则：无需审批、单级审批、条件审批、多级审批；逾期默认不发布。
- 失败规则：自动重试、等待连接恢复、跳过、人工修复后重放、目标回查。
- 多目标语义：某一目标失败不回滚已成功的其他目标；界面显示部分成功。
- 重复保护：相同内容、相同目标账号、相同派生版本默认只交付一次。

## 10. 去水印的产品承诺边界

“去水印”不作为一个模糊按钮出售，而分成：

1. **Clean Source**：优先从用户上传、Google Drive、S3/Dropbox 等获取原始无水印文件。
2. **Static Mark Cleanup**：对用户拥有权利的固定角标执行裁切、补边或静态区域修复，发布前预览。
3. **Dynamic Mark Lab**：移动水印/复杂遮挡，仅作为后续实验能力，有质量提示和强制审批。

TikTok Display API 官方公开能力集中在用户资料和公开视频元数据，没有提供可据此承诺的原始无水印媒体下载；商业产品不能借用面向非营利研究的 Research API。[TikTok Display API](https://developers.tiktok.com/doc/display-api-overview/)

## 11. 商业化和收费方式

### 11.1 收费单位

不要只按席位或“视频条数”收费。建议组合计量：

- 活跃工作流数量。
- 已连接账号/存储连接数量。
- 每月媒体处理分钟。
- 成功交付次数。
- 对象存储和外网流量。
- 并发处理数和数据保留期。
- 高成本 AI/ASR/翻译用量；支持 BYOK 或用量加价。

### 11.2 套餐方向（用于价格实验，不是最终定价）

| 套餐 | 目标用户 | 核心边界 |
| --- | --- | --- |
| Starter | 单人创作者 | 少量工作流/连接、基础适配、手动审批、短保留期 |
| Creator Pro | 高频创作者/小团队 | 更多分钟、多目标自动发布、V1 深度本地化、日历和恢复 |
| Team / Agency | MCN/代运营 | 多工作区、成员权限、多级审批、客户报表、更长历史 |
| Enterprise | 品牌/大型机构 | SSO、审计导出、私有连接器、专属限额、部署与 SLA |

价格测试可以从人民币月付 `¥99–199`、`¥399–699`、`¥1,499+` 三个心理区间开始，但必须先用 10–20 个目标客户访谈和真实处理成本校准；不能在尚无连接器稳定性和单位经济数据时锁死价格。

### 11.3 增长路径

- 免费试用以“成功建立一条自动化并完成一次 dry run”为激活目标。
- 模板市场按场景获客，如“YouTube → Bilibili 深度本地化”“云盘原片 → 抖音/YouTube 多发”。
- 代理商套餐通过多客户空间、审批和报告形成高客单价。
- 平台审核未完成的连接器不得用预售话术包装成现成功能。

## 12. 里程碑与资源估算

| 阶段 | 时间 | 交付物 | 决策门 |
| --- | ---: | --- | --- |
| Phase 0 可行性 | 2–3 周 | 平台申请清单、Temporal PoC、YouTube→Drive 垂直切片、能力矩阵 | 动态图、暂停/恢复、幂等与成本是否通过 |
| Phase 1 控制面 | 4–6 周 | Workspace、Connection、Workflow/Version、内容模型、基础 API | 草稿与发布版本隔离、凭证安全通过 |
| Phase 2 连接与执行 | 6–8 周 | P0 来源/目标、触发订阅、运行历史、多目标 Delivery、dry run | 崩溃重启不重复发、部分成功可恢复 |
| Phase 3 处理与治理 | 4–6 周 | FFmpeg 处理、审批、排期、日历、限额、告警 | 成功/失败/恢复路径和 12px UI 验收 |
| Phase 4 Beta 加固 | 4–6 周 | RBAC、计量、分析、安全、长稳、平台审核收口 | Beta 准入矩阵通过 |

合理预期：3–5 人有经验团队约 5–7 个月完成 V2 Beta；单人开发更可能需要 9–15 个月。平台应用审核时间不包含在纯工程工期内，可能成为关键路径。

## 13. V2.0 明确不做

- 不做无限自由的通用自动化画布。
- 不开放任意代码执行节点。
- 不承诺任何公开视频都能无水印获取。
- 不承诺未经平台审核即可公开自动发布。
- 不一次性实现二十个平台；按连接稳定性和真实用户路径逐批上线。
- 不为追求 exactly-once 宣传而掩盖外部平台的不确定性；使用幂等、回查和对账解决。
- 不删除 V1；V1 作为复合动作和兼容适配器继续创造差异化。

## 14. 北极星指标和护栏指标

北极星指标：**每周成功自动交付的合规内容数**。

配套指标：

- 首条工作流发布时间、首个成功交付时间。
- 活跃工作流数、7/30 天留存。
- 无人工干预完成率、审批后完成率。
- 成功交付率、重复发布率、未知状态率。
- 平均恢复时间、连接断开恢复时间。
- 每处理分钟成本、每成功交付毛利。
- 因平台政策、内容权利或审核导致的阻断数。

## 15. 下一步执行顺序

1. 启动平台开发者主体和应用申请，不等待代码完成后再申请。
2. 用 Temporal 做 2 周技术 PoC：动态受约束图、长任务心跳、暂停、审批等待、发布回查。
3. 完成 YouTube 频道触发 → 规范化 → Google Drive 备份的无风险垂直切片。
4. 再接入一个真实发布目标，验证幂等、部分成功和平台限流。
5. 完成向导 UI、不可变版本和 dry run 后，才开放内测用户配置工作流。
6. 用 5–10 个真实团队工作流校准平台优先级、套餐和处理成本。
