# Visoraft V2 研究发现

## 产品代际结论

- V1 是固定纵向深度链：发现内容、下载、字幕识别、翻译与质检、转码、审核、投稿。
- V2 是横向多平台自动化产品：连接来源与目标、配置触发和处理、发布不可变工作流版本、持续无人值守执行。
- V1 应作为 V2 的内置复合动作 `LocalizeForChina`，而不是成为 V2 的领域模型。

## 竞品结论

- Repurpose.io 的价值单位是持续运行的工作流，不是单次批量发布；关键成熟度来自来源范围、自动/排期发布、限额、连接健康、重连、跳过/重放、备份、媒体兼容、日历和失败诊断。
- 平台能力必须按来源/目标角色、媒体类型、账号类型、权限、触发方式、发布方式和限制建模，不能用一个“已支持”布尔值表示。
- Zapier、Make 和 n8n 证明了条件分支、错误处理、历史输入重放、草稿/发布版本和子工作流的重要性；V2 首版应采用受约束向导，不直接复制无限自由画布。
- Buffer 和 Sprout Social 证明无人值守仍需账号级 RBAC、待审批发布权、多级审批、过期处理和全渠道日历。

## 官方平台边界

- YouTube 可用频道推送触发和 OAuth 上传；搜索/分类发现仍需 Data API 轮询。
- TikTok Display API 主要提供公开视频元数据，不提供可承诺的原始无水印文件；Direct Post 正式公开发布依赖应用审核和用户授权。
- Google Drive 同时适合作为来源和备份目标，但 webhook channel 会过期，必须续租。
- Bilibili V2 应优先开发官方开放平台连接器，V1 Cookie 适配器仅作为兼容模式。
- 抖音公开发布能力依赖开发者主体、应用审核和用户授权；这些是外部发布门槛，不能按纯编码任务承诺日期。
- Instagram 本轮官方资料读取受限，当前只列候选，不列已确认交付范围。

## 处理与可靠性边界

- “去水印”拆为原始无水印资产优先、固定角标裁切/修复、动态水印实验三层；禁止承诺任意平台一键无损去水印。
- V2 使用 `draft -> validate -> publish immutable version`，每次运行绑定具体工作流版本。
- 外部发布采用内部至少一次执行、目标幂等指纹、状态回查和不确定结果对账，不虚构跨平台严格 exactly-once。
- 首版工作流必须显式防止内容回流和循环触发：来源指纹、origin chain、最大跳数、目标回流检测和默认禁止同平台闭环。

## 执行引擎技术选型

- Temporal 官方模型提供持久工作流执行、故障后按事件历史恢复、活动重试与心跳检查点、暂停/恢复、计时器和子工作流；这些正对应媒体处理、人工审批、平台限流和不确定发布回查等长时任务。
- n8n 很适合借鉴产品交互，但不适合直接作为 Visoraft V2 的商业内核：其 Sustainable Use License 明确限制把 n8n 实质能力作为面向客户的商业产品，嵌入画布需要单独 OEM 商业条款；外部二进制 S3 存储、共享和部分治理能力也受商业版本限制。
- 推荐的主方案是“自研产品控制面 + Temporal 执行面 + 现有 V1 服务适配层”，而不是嵌入 n8n，也不是继续无限扩张 V1 固定状态机。正式实施前需做一个两周 PoC，验证动态受约束 DAG、取消/暂停、媒体 Activity 心跳、审批等待和发布对账。
- 若团队暂时无法承担 Temporal 运维，可把 Temporal Cloud 与自托管成本列入 PoC 对比；不建议直接回退到无事件历史的内存编排。任何临时自研执行器都必须遵守相同的不可变版本、节点运行记录、幂等和恢复契约。
